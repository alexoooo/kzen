### Severity rubric (recap)

- **Critical** — used API is *scheduled for removal* in next major; compile *will* fail.
- **High** — deprecated with replacement available now; or JDK terminal-deprecation that will trip on next JDK bump.
- **Medium** — opt-in markers, version mismatches that could cause runtime drift.
- **Low** — stylistic redundancy; code is correct.
- **Info** — environmental nags unrelated to source.

### Effort rubric (recap, per occurrence)

- **Trivial** — IDE quick-fix or single-token edit.
- **Small** — one-file edit, no API change. <30 min.
- **Medium** — multi-file refactor confined to one sibling. <2 h.
- **Large** — cross-sibling refactor. Days.
- **Blocked** — fix requires upstream library release; track only.

## Proposed fixes (per category) — no edits applied

### Category A — Critical Kotlin (K01) — *Do first; trivially fixed; blocks Kotlin 2.5*

- **Scope:** 1 file: `kzen-lib/kzen-lib-common/src/commonMain/kotlin/tech/kzen/lib/common/model/attribute/AttributeSegment.kt`
- **Fix:** Add `@ConsistentCopyVisibility` on the `data class AttributeSegment` declaration (per Kotlin's recommended migration). Confirm there are no external callers using the auto-generated `copy()` to instantiate with the non-public primary constructor — a quick grep across the composite for `AttributeSegment(` instantiation sites should establish this. If any exist, switch them to a public factory.
- **Risk:** Very low — annotation is the documented forward-compatible path. No bytecode shape change for callers using the public constructor.
- **Suggested PR boundary:** Single commit on `kzen-lib`; ripples to consumers via mavenLocal after `:publishToMavenLocal` for the three subprojects (per CLAUDE.md cross-sibling version-pin gotcha).

### Category B — High Kotlin (K02) — *Mechanical migration*

- **Scope:** 1 file, 6 import/usage sites in `ReportStore.kt` under kzen-auto-js jsMain.
- **Fix:** Replace `import kotlinx.datetime.Instant` with `import kotlin.time.Instant`. Verify the rest of `kotlinx.datetime` usage (`Clock`, `LocalDateTime`, etc.) still imports from `kotlinx.datetime` — only `Instant` moved.
- **Risk:** Low — `kotlin.time.Instant` is API-equivalent for the operations on a typealias. Confirm via build.
- **Suggested PR boundary:** Single commit on `kzen-auto`. No cross-sibling impact.

### Category C — Medium Kotlin (K03) — *Annotation-only*

- **Scope:** 1 site at `FeatureController.kt:496` in kzen-auto-js jsMain.
- **Fix:** Add `@OptIn(kotlin.js.ExperimentalWasmJsInterop::class)` either on the call-site function or at file level.
- **Risk:** Negligible — opt-in is just acknowledging the API stability tier. No behavioural change.
- **Suggested PR boundary:** Bundle with Category B in the same kzen-auto-js commit.

### Category D — Low Kotlin (K04, K05) — *Style sweep*

- **Scope:** Two files in kzen-lib-common (`MirroredGraphStore.kt`, `NotationReducer.kt`) plus one in kzen-auto-jvm (`ReportHeaderReader.kt`). Total 5 source-site edits (drop redundant `!!` and redundant casts).
- **Fix:** IDE → "Cleanup… → Remove redundant `!!`" and "Remove redundant cast" inspections. Verify in-IDE first since the compiler's type narrowing is what made these redundant — the platform-specific compile (JVM vs. JS) might disagree.
- **Risk:** Low. Run kzen-lib-common's tests on both JVM and JS targets before publishing to mavenLocal.
- **Suggested PR boundary:** Two commits — one per sibling — to keep the kzen-lib publish dance independent.

### Category E — JS toolchain (J02) — *Peer-dep alignment*

- **Scope:** kzen-auto-js, kzen-launcher-js, kzen-project-js workspace package.json declarations (KGP-generated; the source is the Kotlin/JS wrappers' BOM dependency declaration in each `*-js/build.gradle.kts`).
- **Fix:** Pin `@mui/material` to `^7.3.11` to match the icons-material peer. Investigate which sibling declares `@mui/material` at the older minor — a `gradle :kotlinNpmInstall --info` from each sibling will surface the resolved version.
- **Risk:** Low if MUI 7 minor versions are API-compatible (they typically are within a major). Could trip a runtime missing-export if MUI 7.3.x removed something. Run kzen-auto's UI dev loop (`BackendDevelopment` + `FrontendDevelopment` per CLAUDE.md) and click-through after the bump.
- **Suggested PR boundary:** One commit per affected sibling; could ship together if all need the same change.

### Category F — Gradle daemon (G01) — *One-line config*

- **Scope:** `kzen-launcher/gradle.properties` only.
- **Fix:** Add `org.gradle.jvmargs=-Xmx2g -XX:MaxMetaspaceSize=1g` (matching the spirit of `kotlin.daemon.jvmargs=-Xmx8g` already present in kzen-auto/kzen-lib).
- **Risk:** None — only affects daemon process JVM allocation.
- **Suggested PR boundary:** Trivial single-line commit on kzen-launcher. Could pair with a sweep across siblings to standardize `org.gradle.jvmargs` everywhere.

### Category G — Blocked / Track-only (J01, J03, V01) — *Watch upstream*

- **J01 yarn CJS aliases:** Will resolve when KGP defaults away from yarn classic, or when kotlin-wrappers' transitive dep tree drops the CJS aliases. No local action recommended.
- **J03 node DEP0169:** Same root cause (yarn 1.x using `url.parse`). Will resolve via the same upstream change.
- **V01 sun.misc.Unsafe:** Watch [`net.openhft:zero-allocation-hashing`](https://github.com/OpenHFT/Zero-Allocation-Hashing) for a release that drops Unsafe. Until then it's a runtime warning at test time only — does NOT block the build, does NOT affect production runtime. If JDK eventually removes the method, the alternative is to swap `zero-allocation-hashing` for another fast-hash library (e.g. `com.appmattus.crypto:cryptohash-kotlin`); that's a Medium-effort source touch in whichever module uses XXHash today.

### Skipped: Category E (J02 — `@mui/material` peer mismatch)

Investigation showed `kotlin-js-store/yarn.lock` resolves `@mui/icons-material@7.3.11` against `@mui/material@5.18.0` — a major-version drift introduced because `kotlinWrappers.mui.material` (BOM 2025.12.11) pins MUI v5 while `muiIconsVersion = "7.3.11"` is our v7 pin. Both sides cannot easily move:

- Bumping kotlin-wrappers past 2025.12.11 is **blocked** per CLAUDE.md (removes `kotlin-react-legacy`; React `key` typing change; coordinated `kzen-auto-js` + `kzen-launcher-js` touch-up needed).
- Downgrading `muiIconsVersion` to a v5-compatible release would lose icons added in v6/v7.
- Pinning `npm("@mui/material", "7.3.11")` ourselves would override the BOM with an API-incompatible major and very likely break `kotlinWrappers.mui.material` Kotlin bindings at runtime (no compile-time guard).

**Recommendation:** leave J02 in place until the kotlin-wrappers ceiling is lifted in a coordinated React-DSL PR; at that point MUI v7 bindings come along for free.
